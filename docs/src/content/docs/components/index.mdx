The web components are framework-free custom elements built on native elements, with no runtime dependency: a `gw-button` is a `<button>`, a `gw-dialog` is a `<dialog>`, a `gw-segmented` is a set of radio buttons. Keyboard use, focus and forms come from the browser. They're styled only through `--gw-*` variables, so each follows whichever theme and mode surrounds it.

Every demo on these pages has a theme and mode picker. Pick one and the components follow it.

## Taking them into an app

Components and tokens ship as packages, `@timmo001/groundwork-ui` and `@timmo001/groundwork-tokens`, on npm and JSR. Each release rolls out to the apps that use them, so nothing waits on Renovate:

```sh
bun add -E @timmo001/groundwork-ui @timmo001/groundwork-tokens
```

```ts
import "@timmo001/groundwork-tokens/themes.css";
import "@timmo001/groundwork-ui";
```

Set `data-gw-theme` and `data-gw-mode` on a container, and everything inside follows. Extend a component by wrapping it, or through its variables and `::part()`. A change every app needs goes into Groundwork instead.

The packages aren't published yet. Until they are, apps keep the copies the [sync](/sync) gave them.

## Fields stay in light DOM

Password managers and `<label for>` can't reach into a shadow root, and a form only submits the controls it can see. So `gw-input`, `gw-select`, `gw-checkbox` and `gw-switch` render their native control in light DOM, and adopt their styles into whichever document or shadow root they're in. Pages with credentials keep the whole form out of shadow roots.

## Icons

Components that show an icon take it as path data in an `icon` attribute, or an `<svg slot="icon">`. [Iconography](/foundations/iconography) covers picking a set and when to show an icon on its own.
