The web components are framework-free custom elements built on native elements, with no runtime dependency: a `gw-button` is a `<button>`, a `gw-dialog` is a `<dialog>`, a `gw-segmented` is a set of radio buttons. Keyboard use, focus and forms come from the browser. They're styled only through `--gw-*` variables, so each follows whichever theme and mode surrounds it.

Every demo on these pages has a theme and mode picker. Pick one and the components follow it.

## Taking them into an app

Components and tokens ship as packages, `@timmo001/groundwork-ui` and `@timmo001/groundwork-tokens`, on npm. Each release rolls out to the apps that use them, so nothing waits on Renovate:

```sh
bun add -E @timmo001/groundwork-ui @timmo001/groundwork-tokens
```

```ts
import "@timmo001/groundwork-tokens/themes.css";
import "@timmo001/groundwork-ui";
```

That defines every element. To define only some, import each one's `define/` entry, such as `@timmo001/groundwork-ui/define/gw-button.ts`, which also defines the elements it renders. An element's own file, such as `gw-button.ts`, exports the class and defines nothing, so it can be extended or registered under another tag. A tag another class already holds is left to it, with a console warning.

### Building from parts

Every composite is built from the base elements in the table below, rendered as themselves rather than copies, so a change to a `gw-button` or `gw-input` reaches every menu, table and filter that holds one. Each base element works on its own too: an app that wants only the theme picker's mode control takes `gw-segmented`, and one that wants a pick list in a side panel takes `gw-option-list`. The pieces inside a composite are its parts, so `::part(search)` on a table reaches its `gw-input`.

```ts
// Only the elements this page uses, and what they render
import "@timmo001/groundwork-ui/define/gw-segmented.ts";
import "@timmo001/groundwork-ui/define/gw-option-list.ts";

// A button of the app's own, on Groundwork's, neutral unless it says otherwise
import { GwButton } from "@timmo001/groundwork-ui/gw-button.ts";

class AppButton extends GwButton {
  constructor() {
    super();
    this.variant = "neutral";
  }
}

customElements.define("app-button", AppButton);
```

### Helpers

The behavior the composites share is exported on its own too, for an app's own elements that should move and open the same way:

- `listIndex(key, index, length, page?)` gives the index a list key moves to: the arrow keys step and wrap, Page Up and Down jump eight and stop at the ends, Home and End go to them. `gw-option-list` and `gw-menu-button` move with it.
- `placeBeside(popup, anchor, { align, gap, fit })` puts a fixed popup under the control that opened it, or over it when there's more room there, lined up with its start edge or, with `align: "space"`, the edge on the roomier side of the window. It sets `data-placement` and `data-side` for styles that follow the side. `gw-popover` and `gw-select` open with it.
- `Below` follows whether the window is narrower than a CSS length, as the `*-below` attributes do.
- `DirtyState` follows whether a form's values differ from what was last saved: `start(value)` when it loads, `update(value)` on each edit, `markClean()` after a save, and `subscribe(listener)` to enable Save only while something changed. While any one is dirty, closing or reloading the tab asks first, and `confirmLeave()` asks in a `gw-dialog` before the app moves to another page, putting the forms back as they were saved if someone leaves. Its `discard` option is how a form puts itself back. `hasUnsavedChanges()` reads the whole page, and `gw-unsaved-changes` fires on `window` each time that changes.

```ts
import { DirtyState, confirmLeave } from "@timmo001/groundwork-ui";

const dirty = new DirtyState<Settings>({ discard: () => show(saved) });

dirty.start(saved);
form.addEventListener("input", () => dirty.update(read()));
dirty.subscribe((changed) => (save.disabled = !changed));

const router = makeRouter(routes, { beforeLeave: () => confirmLeave() });
```

```ts
import { listIndex, placeBeside } from "@timmo001/groundwork-ui";

const place = () => placeBeside(menu, button, { align: "space" });

menu.addEventListener("toggle", (event) => {
  if (event.newState === "open") place();
});
addEventListener("resize", place);
addEventListener("scroll", place, true);

menu.addEventListener("keydown", (event) => {
  const items = [...menu.querySelectorAll("button")];
  const index = items.findIndex((item) => item === document.activeElement);
  const next = listIndex(event.key, index, items.length);

  if (next === undefined) return;

  event.preventDefault();
  items[next]?.focus();
});
```

Set `data-gw-theme` and `data-gw-mode` on a container, and everything inside follows. A change every app needs goes into Groundwork; a look only one app wants stays in that app, as below.

## Your own look

An app can take the components without taking their look. Nothing is forced: each layer below changes only what it names, and the rest keeps following the theme.

- **Variables.** Every element lists its `--gw-*` CSS properties, such as `--gw-popover-width` or `--gw-spinner-size`. Set them on the element or any container above it.
- **Tones of your own.** `--gw-tone`, `--gw-tone-fill` and `--gw-tone-border` color a chip, badge, dot, alert, banner or notification with any color, such as the [app tones](/themes#app-tones) solved for every theme.
- **Parts.** Each piece inside a shadow root is exposed as a part, listed under `@csspart` in the element's docs and editor hovers, so `::part()` reaches the surface, heading, body, rows and labels. A lint check fails the build when a rendered part goes undocumented, or a documented one no longer renders. The fields render in light DOM, so their classes are styled as they are.
- **Wrapping.** For markup or behavior of your own, wrap the element in one of yours and keep its attributes and events.
- **Your own tokens.** An app with its own variables can point them at Groundwork's, such as `--app-surface: var(--gw-color-surface-raised)`, and keep its stylesheets as they are.
- **Plain CSS wins.** The elements' styles are in the `groundwork.components` cascade layer and the tokens in `groundwork.tokens`, so an app's CSS outside a layer wins over them without matching their selectors or adding `!important`. That's how the fields' light DOM classes take a page's own rules. See [Overriding tokens](/themes#overriding-tokens).
- **Hidden and reduced motion.** In a shadow root, `hidden` and the reduced motion rules sit in a `groundwork.state` layer above the components, with no `!important`, so a page's rule on an element or a part still wins: keep a skeleton pulsing, or show a hidden element its own way. Under reduced motion everything stops but a loading ring's turn, which shows something is still happening.

The same badge, as it comes and with an app's own shape: square corners, a tone stripe, an uppercase label and a monospace value. Pick another theme and both follow it.

## Sizes and density

Controls share one set of sizes, `xs`, `small`, `medium`, `large` and `xl`, set with `size` on buttons, menu buttons, inputs, selects, segmented controls, chips, badges and setting rows. Each also has a `--gw-<element>-scale` property for any size in between, such as `--gw-badge-scale: 0.7`.

Heights and icons also follow the theme's density through `--gw-control-scale`: 0.85 in compact themes, 1 in normal ones and 1.1 in roomy ones. Text and padding keep to the size alone, so a compact theme gets shorter controls without smaller words. Pick a compact or roomy theme to see these change:

## Using with Lit

The elements work in Lit templates as they are. The package ships a Custom Elements Manifest, `custom-elements.json`, generated from each element's docs, so editors and `lit-analyzer` know every tag, attribute and its values:

```sh
bun add -DE lit-analyzer typescript@5
bun x lit-analyzer src --strict
```

```text
Type '"nope"' is not assignable to '"brand" | "neutral" | "info" | "success" | "warning" | "danger"'
5:  <gw-button variant="nope">Save</gw-button>
```

`lit-analyzer` needs TypeScript 5, so keep it apart from a TypeScript 7 typecheck.

For events, `on()` adds a listener typed from the element's docs and returns a function that removes it. A `pick` handler gets `CustomEvent<{ value: string }>` with no cast, and an event the element doesn't fire won't compile:

```ts
import { on } from "@timmo001/groundwork-ui";

const off = on(menu, "pick", (event) => open(event.detail.value));
```

| Element | Events |
| --- | --- |
| `gw-command-menu`, `gw-option-list` | `pick`, with `detail.value` |
| `gw-menu-button` | `select`, with `detail.value`; `check`, with `detail.value` and `detail.checked` |
| `gw-dialog`, `gw-popover`, `gw-sheet` | `close` |
| `gw-select` | `change` |
| `gw-segmented` | `change`; `pick`, with `detail.value`, on every pick, the chosen option included |

## Accessibility

Each element is built on the native control that does its job, so keyboard use, focus and forms come from the browser, and an axe pass over every docs page in every core theme and mode fails the build when a component loses its name or a theme drops a contrast pair.

- **Keyboard.** Buttons, links, checkboxes and radio groups behave as their native elements do. Menus, selects, option lists and the command menu move with the arrow keys, Home, End and Page Up or Down, pick with Enter and close with Esc. Popovers, sheets and dialogs close on Esc, following the [closing rules](/components/overlays#closing).
- **Focus.** Every control shows a ring in `--gw-color-focus` on keyboard focus, `--gw-focus-width` wide and `--gw-focus-offset` out. Overlays move focus in when they open, to the close button so Enter never confirms by accident, and back to what opened them when they close.
- **Names.** A control's text is its accessible name. When `labels="hide"` or `labels="auto"` hides it, or `label-hidden` hides a field's label, the text stays as the name and the tooltip. Icon-only controls inside composites, such as close, clear, reveal and (i) buttons, have names of their own, set with `*-label` attributes.
- **Other languages.** Every word an element shows or announces on its own has an attribute, such as `close-label`, `no-match-label`, `pick-hint` or `pick-key`, defaulting to English. Each is listed in the element's API reference below its page.
- **Reduced motion.** Under `prefers-reduced-motion: reduce` everything stops but a loading ring's turn, which shows something is still happening.
- **Forced colors.** In Windows' contrast themes and other forced colors, where the browser drops fills and tints, anything whose state shows only as a fill draws it in system colors instead: a pressed or current button, the chosen segment, a switch that's on, meter and gauge fills, the focused menu item and the active option. Theme previews keep their colors, since they're pictures of a theme.

```html
<!-- Only the icon shows, and "Refresh" stays the name and tooltip -->
<gw-button labels="hide" icon="…">Refresh</gw-button>

<!-- The search field's name and empty line in French -->
<gw-filter label="Hôte" search-label="Rechercher" no-match-label="Aucun résultat" clear-label="Effacer"></gw-filter>
```

## Fields stay in light DOM

Password managers and `<label for>` can't reach into a shadow root, and a form only submits the controls it can see. So `gw-input`, `gw-select`, `gw-checkbox` and `gw-switch` render their native control in light DOM, and adopt their styles into whichever document or shadow root they're in. Pages with credentials keep the whole form out of shadow roots.

## Icons

Components that show an icon take it as path data in an `icon` attribute, or an `<svg slot="icon">`. [Iconography](/foundations/iconography) covers picking a set and when to show an icon on its own.

## No jumps on load

A page shouldn't move while its components load. Before a `gw-` element's script defines it, `themes.css` gives it the display and size it will have once it upgrades: buttons keep their height, padding and label width, fields keep their label and hint rows, layouts keep their flow, and dialogs, popovers and menus stay hidden until they're opened.

- Size content that a script fills in (a chart, a list from a server) with a skeleton of the same size, so the real content replaces it in place.
- Reserve room for anything that appears after load, such as a banner or a header control, rather than pushing the page down.
- Animate entrances with opacity and transforms, which don't move anything around them.

## Scrollbars

`themes.css` gives the page and everything in it small scrollbars: a rounded thumb in the theme's secondary text color on a clear track, with no arrow buttons, a little stronger on hover. The thumb squares off where it meets the top or bottom of its track, or either end of a sideways one. There's nothing to set up. Restyle them anywhere with `--gw-scrollbar-size` (0.4rem by default), `--gw-scrollbar-thumb` and `--gw-scrollbar-track`, or hide one with `scrollbar-width: none`. The rules are in the tokens layer, so any rule of a page's wins. Firefox, which has no WebKit scrollbar styling, shows its own thin scrollbar in the same colors.

Inside components, such as a menu's items, a list or a table, the scrollbars are thinner and fainter until hovered, so they keep out of the way of what they scroll. Restyle every component's with `--gw-scrollbar-inner-size` (`0.25rem`), `--gw-scrollbar-inner-radius` (the size, fully round), `--gw-scrollbar-inner-thumb`, `--gw-scrollbar-inner-thumb-hovered` and `--gw-scrollbar-inner-track`; unset, they follow the page's `--gw-scrollbar-*` properties. Each element also takes its own, named after it, so one can differ from the rest:

```css
gw-menu-button {
  --gw-menu-button-scrollbar-radius: 0;
}

gw-table {
  --gw-table-scrollbar-size: 0.375rem;
  --gw-table-scrollbar-thumb: var(--gw-color-accent);
}
```

Every element has `--gw-<element>-scrollbar-size`, `-radius`, `-thumb`, `-thumb-hovered` and `-track`. Add `scrollbars` and `scrollbarHooks("my-element")` to an app's own component's styles to give it the same scrollbars and hooks.

The square ends follow each scroller's scroll through the `gw-scrollbar-edges-y` and `gw-scrollbar-edges-x` animations, which components run on their own scrolling parts and the ui package keeps in step for the page. A scroller of your own keeps round ends unless it runs them too:

```css
.my-list {
  animation:
    gw-scrollbar-edges-y linear both,
    gw-scrollbar-edges-x linear both;
  animation-timeline: scroll(self y), scroll(self x);
}
```

The page's rules can't reach inside a shadow root, so an app's own components add the `scrollbars` sheet from the ui package to their styles to match, which also squares their scrollers off:

```ts
import { scrollbars } from "@timmo001/groundwork-ui";

class MyList extends LitElement {
  static styles = [scrollbars, css`...`];
}
```

The docs check every page with a Playwright test that measures the layout shift while it loads. It fails above 0.025, a quarter of the 0.1 the web counts as good, and lists what moved.
